## 2. 主要结果

### 2.1 接口：简报 §8.1 的逐项对应

实现见 `src/adapters/base.py`。

| 简报要求 | 实现 | 要点 |
|---|---|---|
| `load(model_id, dtype)` | 只收注册表的键 | revision 固定；dtype 由调用方给，适配器不自选 |
| `build_inputs(images, instruction, order)` | 支持多张图；两种顺序 | 返回指令、各图、查询 token 的精确区间；指令被模板改写时报错 |
| `generate(..., allowed_token_ids=None)` | `enable_thinking`、`max_new_tokens` 是必填关键字参数，子类不能加默认值 | `allowed_token_ids` 用 logits 处理器，只在这组 token 上取值；`text` 是剥离思考段后的答案；`raw_text` 是全文；计算量字段见 `src/accounting.py` |
| `hidden_states(inputs, layers)` | 返回图像位置与查询位置 | 层号必须由调用方给，不设默认；另收 `query_embeds`，供 E3a 的可学习查询 token 从这里进入 |
| `inject_query_tokens(n, position_mode)` | Qwen：`grid2d`（M-RoPE 二维网格，放在文本之后的新时间索引上）和 `seq1d` | Gemma 与 InternVL 是一维位置，`grid2d` 直接报错，不静默退化（D17、D19） |
| `add_grid_tokens(names)` | 优先复用预留行 | 累计不超过 300 个；单 token 检查；新行用基础词表的均值初始化，嵌入与 lm_head 分别算 |
| `num_layers()`、`hidden_size()` | 有 | |
| （补充）`vision_features(inputs)` | 进入 LLM 之前的视觉 token | 用于 E2 参考线与 E3a 的 C2 对照；冒烟验证它与第 0 层图像位置逐位相同 |

**层号约定（D10，需要你确认）**：
- 层号 0 = 视觉特征并入序列之后的嵌入输出；
- 层号 i = 第 i 个 decoder 层的输出；
- 最后一层取经过最终归一化之后的值；
- 与 HF `output_hidden_states` 的下标一一对应，有效范围 [0, num_layers()]。

## 4. 检查结果

- **仪器零点**：图在前时，两条指令下的图像隐藏状态逐层 `torch.equal`，三个家族全部成立（§2.3 检查 2）。按"仪器先于效应"的规则，这个零点必须是精确的零，现在是。
- **与官方实现的等价**：
  - 输入与官方 processor 逐项相等（检查 1）；
  - 位置 id 与 HF 原生一致（检查 5）；
  - vision_features 与第 0 层逐位相同（检查 6）。
- **跨机器一致**：开发机按服务器条件跑的测试结果与服务器一致（D18）。
- **独立审查**：
  - DEV-0001（指标与统计）：查出 S1 NaN 让 CI 失效、S2 显著性判定不分方向、S3 无分数 AP 依赖图像编号，都已修好。46 个人为植入的变异全部被测试抓住。
  - **G0 接口审查**（只读 agent，CPU 小模型核实；处理见 D21）：
    - 简报 §8.1 的接口全部满足。§12 的陷阱里：
      - "坐标约定"部分满足（Qwen 的框解析在 DEV-0006）；
      - "受限 logits 在训练和推理中一致"部分满足；
      - "LoRA 合并"还没有代码。
    - **阻塞 E1**：
      1. 只有 batch=1 的生成。batch 1 的实测解码速度约 50–80 tok/s，E1 单是 RefCOCO 定位（约 5.7 万句）就要 70–115 GPU 小时。要加批量生成，并报告它与 batch-1 greedy 的一致率。
      2. 图像几何口径未定：Qwen 把图直接拉伸到固定尺寸；InternVL 单 tile 时把 4:3 的图压成正方形，形变 1.33 倍。
    - **阻塞 E3**：
      1. 训练侧没有受限 logits 的交叉熵，也没有统一的"提示 + 助手头 + 目标"训练前向。自写受限输出头时如果漏掉 Gemma 的 logit softcapping，训练和推理就会静默不一致。
      2. 训练后新增的 token 没有重载路径：重新挂适配器再加 grid token，会把训练过的行静默重置为均值。Qwen 与 InternVL 的 grid id 还依赖调用顺序。
    - **次要**：
      - 不传 `query_embeds` 时静默用占位符；
      - LoRA 目标模块应排除视觉塔；
      - `GenerationResult` 缺停止原因；
      - 采样参数会继承仓库或 HF 的默认值；
      - E3a 的开放词汇头缺逐类别名的区间。
    - **备注**：
      - vision_features 与第 0 层逐位相同，所以 E2 的"视觉编码器参考线"就是第 0 层探针本身，不能算两条证据；
      - Gemma E2B 大部分层是 512 滑窗，影响 E6 的长网格输出。
    - **核实无误**：多图顺序、视觉 token 行主序、Qwen 二维查询位置、Gemma 查询位置的 PLE。
- **对照、平凡基线、泄漏检查**：G0 没有训练，不适用。泄漏的预防已经就位：
  - D11：RefCOCO 家族去重、NYUv2 按场景过滤、只有测试划分的基准切出开发子集；
  - D20：P0 探针用过的两张 COCO val2017 图，从所有评测子集中排除。

1. **`is_significant` 的实现解释**（D10(9)）。简报 §8.4 的原话是"差值超过合并标准差的 2 倍，且 bootstrap 95% 置信区间不含 0"。实现是三条规则都满足才算显著：
   - 规则 1：seed 级指标的均值差 > 2 × 合并标准差；
   - 规则 2：按样本配对重采样，每次对各 seed 分别算同一个统计量再取平均，差值的 95% CI 不含 0；
   - 规则 3：两条规则的方向一致。

   另外分"显著更好"和"显著更差"两个方向。**建议确认。**
2. **层号约定**：§2.1 所列。**建议确认。**
3. **E1 的分辨率与视觉 token 策略**（D13-5 规定在 G0 列出）。
   - 现状：Qwen 适配器把每张图强制缩放到固定的 480×640，**不保持长宽比**。竖图会被拉成横图，失真约 1.78 倍，会压低零样本基线。
   - 这个选择还会约束 E3：E3 模型的 T 通道评测要和 E1 基线用同一口径，否则内化带来的增益不可比。独立审查也建议主口径与 E2/E3 相同，另在子集上跑各家族的原生口径作参照。
   - 选项：
     - **(a) 约 300 个视觉 token，尽量保持长宽比（建议）**：
       - Qwen 用 `min_pixels = max_pixels = 300·32²`，由处理器保持长宽比，token 数约 300；
       - Gemma `max_soft_tokens=280`，即它的默认值；
       - InternVL 单 tile，256 个 token；这是官方在 `max_num=1` 时的做法，会压成正方形。另在 E1 的一个小子集上加跑原生动态 tile，量出单 tile 的代价。

       三家 token 数大致对齐，成本最低。E3c 的分块本来就负责补分辨率。需要一个小的开发任务，给 Qwen 适配器加保持长宽比的模式；另一种做法是"横竖两档"（480×640 与 640×480），网格固定、便于批处理，但非 4:3 的图仍有最多 1.33 倍的形变。
       - 注意：Gemma 每个视觉 token 对应 48 px，token 数相近时它看到的像素约为 Qwen 的两倍，报告里写明。
     - **(b) 约 1K 个视觉 token**：Qwen 约 1024，Gemma 1120，InternVL 4 个 tile 加缩略图。prefill 成本是 (a) 的 3–4 倍，E3 训练的显存也更高。InternVL 多 tile 后，图像 token 不再构成一张整图网格，E2/E3 的稠密读出要另想办法。
     - **(c) 维持现状**：Qwen 继续拉伸。不建议。
4. **§5.2 清单里未完成的项推迟**：vLLM/SGLang、前缀缓存、RL 框架、渲染与仿真，分别在需要它们的阶段（E1 或 E4、E3c、E4、E5）开工之前完成。原因之一是装包受磁盘限制（N1）。**建议同意推迟。**
5. **E1 的推理引擎**：现在的适配器是单条样本生成。独立审查估算，batch 1 下 E1 单是定位就要 70–115 GPU 小时，所以批处理是 E1 开跑的前提。
   - **建议**：先在适配器里加 HF 批量生成。它不需要新依赖；在开发子集上报告它与 batch-1 greedy 的一致率。
   - vLLM 等磁盘宽裕后再上；E4 的 rollout 反正要用它。
6. **挂着的 N 项**：
   - **N1 磁盘**：服务器根盘只剩约 5.6 GB，其间别的用户的文件又占掉了约 0.3 GB。E1 的数据落地估计要 3–5 GB，勉强可以放在内存盘，但重启会丢。
   - **N10 数据许可**：阻塞 E1 的数据落地。
   - **N9 检测的标题指标**：E1 要用。
   - **N2 时间线与 GPU 总预算**。

   **E1 预计超过 12 小时**：按硬约束第 8 条，估算会随 E1 预注册提交，请你批准。粗估见附录。
   - N3–N8 属于后续阶段，在对应的预注册之前答复即可。

## 附录：E1 算力粗估（只为 N2 参考；精确估算随 E1 预注册提交）

- **假设**：HF 批量生成；视觉 token 约 300；8 个模型。吞吐按 env_report §7–8 的实测外推：bs16、每条生成 64 token 时，0.8B 为 16.9 条/秒，9B 为 9.8 条/秒。
