# 实战规则（由一次五天 pilot 的事故与发现沉淀，已去项目化）

每条格式：**规则** — 起因。

## git 与工作区
- **共享工作区禁 `git add -A`，管理员逐文件暂存** — 一次 `add -A` 把开发中的 11 个半成品文件
  扫进未审查的 commit 并推送，靠 force-push 抢救。
- **变基后同步所有引用了 hash 的文档** — dev commit 经 rebase 改了 hash，任务书里的校验值随之失效。
- **预授权改动仓库文件后必重跑测试** — 服务器按预授权改了 config 的 num_workers，把"唯一差异"
  测试打红，隔天才被发现。
- **性能键不进"唯一差异"比对** — 测试钉错不变量比没有测试更糟；性能参数（num_workers）允许差异，
  但要有"数值不变"的实证（改前后逐 epoch 损失逐位相同）。
- **服务器的长任务从固定 commit 的 worktree 跑**：多模型的驱动每个模型都开新进程，推中间批前的 `git pull` 会让后面的模型加载新代码，一次运行里就混了两版。
  开跑前 `git worktree add --detach <tmp>/wt<NNNN> HEAD`，所有进程都从那里启动，输出写主仓库的绝对路径；主 checkout 只用来 pull 与推。
- **git stash 是所有 worktree 共用的**：主仓库和各开发 agent 的 worktree 共用一个 stash 栈，裸 `git stash` / `git stash pop` 可能弹出别的会话存的改动。
  合入时要暂存本地改动，用临时 WIP 提交；非用 stash 不可时，用 `git stash push -u -m <唯一标签>`，按 SHA `git stash apply`，再按标签找到条目删掉。
- **重申：不要 cd 进 worktree**。核对 worktree 里的脚本，用绝对路径加 `cd /主仓库 &&` 前缀。2026-10-03 又犯了一次，主工作目录被带走。
- **用 `pgrep -f <模式>` 等进程结束时，模式会匹配到等待循环自己**：命令行里含有同样的字符串，循环就永远不会退出，还会互相卡住。2026-10-03 清理了 6 个这样空转了一天多的循环。
  写法：用 `pgrep -f '[p]ytest tests/'`（方括号技巧，让模式匹配不到自己），或者记下 PID 用 `while kill -0 $PID`，或者直接 `run_in_background` 跑测试本身、等它的完成通知。

## 约定与文档
- **约定只写一处，其余 import；配置注释里的数字用测试钉住** — 网格索引语义被复述后歧义
  （0-based vs 文件名 1-based，搞反整库平移一帧不报错）；模态名的连字符/下划线两份映射分叉，
  守卫失效重复下载。
- **裁定编号只追加不插入** — 三次把新条插到旧条前面，编号乱序需要返工。
- **台账/文档的脚本编辑必须带命中断言** — `str.replace` 静默未命中让两行台账丢失，后续编辑连锁失效。
- **heredoc 里含中文引号的 python 用三引号** — 一次 SyntaxError 让三处编辑全部没应用而 commit 照推。
- **任务书里"与 X 完全对齐"之类的定量主张先算再写** — 一次注释里的对齐声明与实际相差 155 倍。
- **zsh 里不要用字符串变量拼命令参数** — `for m in "" "--model x"; do cmd $m; done` 在 zsh 里 `$m` 不分词，
  `--model x` 被当成一个参数，argparse 报错退出码 2，被误判为"冒烟失败"。用数组，或者把参数直接写出来；
  判定失败之前先看落盘的错误信息。
- **任务书里的命令逐字对照脚本的参数定义** — 写了 `--dtype bfloat16`，脚本的 argparse 只接受 `bf16`；
  服务器照抄就会在参数解析时失败。写命令前先看一遍 `--help` 或 argparse 的 choices。
- **任务书里的 shell 片段每行只写一个 export** — `export ROOT=/a PROJ=$ROOT/b` 这一行里 `$ROOT` 在赋值前
  就被展开成旧值（空），PROJ 变成 `/b`、HF_HOME 指到项目外的根盘；服务器 CC 实测发现。写进任务书、
  值守说明、启动脚本的环境块，一律一行一个。

- **并行 worktree 任务合入后，在干净的临时 worktree 里对合入 commit 跑全量测试**：先合入的任务改了公共接口
  （返回值从二元组改成三字段），后开的 worktree 的测试仍按旧接口写，各自在自己的分支上都是全绿，合到一起才红。
  主工作区如果有别的会话的半成品，不要在主工作区跑测试判断合入结果。
- **管理员不要 `cd` 进 agent 的 worktree** — Bash 工具会把主工作目录切过去，之后以为在主仓库里做的 git 操作
  其实落在 agent 的分支上；同一项目里犯了两次。对 worktree 一律用 `git -C <路径>`，跑测试用子 shell
  `(cd <路径> && …)`。
- **验证合入时，在临时 worktree 里完成合并与冲突解决，再把主分支 `--ff-only` 快进到那个验证过的提交** —
  这样进主分支的正是跑过全量测试的那个 commit，不会有"验证的是 A、合入的是 A′"的缝隙。两个 agent 都往
  `requirements.txt` 末尾追加依赖，是最常见的非功能冲突：保留两边，由管理员在合并提交里注明。

## 仪器
- **null 臂必须精确为零，不是约等于零；开确定性算法后逐位比对** — 统计判据会让小泄漏以
  measurable=False 通过，与健康仪器无法区分。
- **两条独立代码路径的等价性作为免费校验** — 并行绑定 vs 门控顺序数学等价，同 seed 逐位比对。
- **逐位比对只在 RNG 流未分岔的位置成立** — 第 3 位 graft 的 RNG 消耗与 shuffle 排列不同，
  数值必然不同，那是构造性质不是泄漏；范围要显式限定。
- **断言放在证据落盘之后** — null 臂真出问题时手里要有表可回传，不只剩 traceback。
- **CSV 往返精度**：pandas `read_csv` 默认在 15 位有效数字截断；比对逐位相等时用
  `float_precision="round_trip"`，或直接比 CSV 原始字符串。
- **AdaptiveAvgPool 的 CUDA 反向在确定性模式下会抛错**，用 `mean` 替代（输出 1×1 时等价）。
- **测试路径用小型随机 backbone，不下载权重**；合成 fixture 故意 H≠W 抓轴序错误。
- **断言用的 fixture 要在被断言的量上取值互不相同** — 掩码全是居中方块 ⇒ 方形网格恒等于自己的转置，
  转置变异照样通过；同一批里两条样本的计数恒等 ⇒ "整批取第一条"的变异照样通过。
  形状非对称（H≠W）只挡住一半，**内容**与**批内**也要非对称。

## 跨机器差异（开发机绿、算力机红）
- **开发机上无法产生差异的属性，测试等于没写** — device、dtype、内存布局、对象同一性四类：在 CPU/tiny 上
  `assert x.device == "cpu"` 或把同一个对象同时塞进两处，删掉被测代码照样绿。一个项目里连续三次栽在这上面
  （张量布局末位差 1e-6、bf16 下可训练参数 dtype 不匹配、进模型的 batch 从未搬到 GPU）。
- **两条腿钉住**：① 代码里的**入口断言**——在任何算子之前比较 device/dtype/布局，抛自有异常并报出两个值，
  任何机器都会触发；② 算力机上的**一次运行时审计**——forward-pre-hook 挂满子模块，首个不符即停并报模块名。
  开发机跑不出真结论，但审计能在一次冒烟里穷尽全路径，包括崩溃点之后从未执行的代码。
- **`meta` 设备是开发机唯一能做的真检查** — 模块搬到 meta、输入留 cpu，纯 Python 的入口断言照样触发，
  而 `cpu → cpu` 的搬运是空操作、测不出任何东西。
- **可选加速包在两台机器上不一致时，CPU 测试路径要显式选定实现** — 服务器装了只支持 GPU 的 Triton 内核包
  （fla），transformers 在 import 时就把模块级函数全局绑定过去，与张量设备无关；开发机没装，走 torch 回退。
  于是 CPU 上的小模型测试在开发机全绿、在服务器 16 个红。做法：适配器在 CPU 上用上下文管理器显式换成
  torch 实现，并在开发机上用"模拟已安装"的桩测试钉住；冒烟信息里记录实际走的实现。
- **配置等价性按规范化键值比，不按文本行 diff** — 两份 YAML 排序与注释不同会产生几十行噪声，
  被误读成"唯一差异"约束被破坏。
- **程序生成的数据要跨机器逐位复现，数据路径上就不能有平台相关的浮点** — 一个合成数据生成器在 arm64 macOS
  与 x86_64 Linux 上，10 个钉住摘要有 2 个不同。定位靠"逐分量子摘要"（场景规格、图像、各 mask、元数据分别
  取哈希）：场景相同而某个物体的 mask 不同，指向编译过的光栅化（C 代码里的乘加在 arm64 上可能被融合成 FMA）；
  只有元数据不同，指向写进元数据的未量化浮点。可能的来源还有平台 libm 与 numpy 的超越函数、SIMD 改变的求和
  顺序。做法：整数光栅化、decimal 三角函数、定点求和、元数据只写量化值；第三方 C 引擎（物理仿真）管不了的，
  指定规范平台只在那里生成，其余平台上的比对跳过并写明原因。钉住摘要的清单要足够大（这里从 10 个扩到 180 个）。
- **计时类测试会被并行负载拖垮**：模式 B 下开发 agent 常与管理员的复验同时跑测试，按 CPU 时间计的速度门槛（例如生成器 ≥ 20 条/秒）可能偶发失败。
  失败时先单独重跑那一条，看负载（`uptime`），不要急着判回归；门槛余量低于 30% 时，记下来交给下一个开发任务处理。

## 评测与报表
- **批量生成必须与逐样本生成逐 token 相同，把它写成测试** — 一处 `min(prompt_len)` 的整批截断让每对样本里
  长的那条从 prompt 中途开始生成，47% 的样本产不出锚点 token；报出来的"free-running 只有 teacher-forced 的一半"
  完全是工具缺陷，未受污染的样本上两者差 0.0002。差点成为论文里一条假的 train-test gap。
- **报告里的数字一律由脚本从产物读取生成，不手打** — 凭印象打了四行台账数字，三次运行里第三次犯；
  自查要覆盖每一个数字与每一个分层的存在性，不是抽样。
- **完美或方向相反的指标先当混淆查，别急着下结论** — "只喂 GT 区域"比"喂全图"低 6 点，看着像"选择性没用"，
  实则训练每步喂 179/256 格而 GT 中位数只有 9 格，全部样本都在训练分布外；干净的判据是**同预算**下比位置。
- **空集合报 null，不能与"全错"同形** — 快评样本里恰好没有正类，`mean([])` 返回 0.0，被打印成"准确率 0.000"。
- **完美的指标先当泄漏查** — 拒答准确率 6/6 = 1.000，因为 no-target 样本的指令字面就是"无"，
  任务可由字符串匹配平凡判定；该数度量的不是模型能力。
- **少数类重采样要按它的信息量定比例，不是无脑 1:1** — 23 条负例被 1:1 采样后每 epoch 各抽 45 次、
  吃掉一半算力，而它们的主损失项被跳过、任务又平凡可解。

## 实验设计
- **中介变量从第一次运行就记** — 事后补不了；正是它把两个数据集的相反结论统一成一个机制。
- **诊断前预注册预测**，事后标注兑现与否 — 预测对错各半的那次比全对的那次更有信息。
- **跨数据集匹配优化步数而非 epoch** — 固定 epoch 数把数据集规模差异换算成 8–155 倍步数差异，
  成了未被识别的主导变量。
- **控制组的"容易程度"要与处理组匹配** — 可死记的噪声控制看起来"无害"只是因为它在短预算下
  几乎没动；换个预算就翻转。
- **判据满足 ≠ 问题回答** — 效应可测（GO）与"哪种机制/哪一行决策表"是两个层次；可学性诊断
  （训练损失是否低于 ln K）先于任何 overlap/累积解读。
- **不对已知不完整的数据做试探性构建** — 一次多余的 build 吃了 10 分钟并拖慢并行任务。

## 长时间自主运行
- **往用户的云盘上传后，不要用 `rclone link` 取链接** — 它会顺手把文件设成"任何知道链接的人可读"，等于公开分享了包里的代码。上传后用 `rclone lsjson --metadata --drive-metadata-permissions read` 核对权限，只该有所有者；要分享由用户自己操作。误开了就删掉文件重新上传。
- **账户的会话用量上限会同时停掉所有 agent 和管理员自己** — 三个 Opus 子 agent 并行跑了几个小时就撞上限，
  两个开发 agent 半途中断，直到窗口重置。做法：同时在跑的 agent 不超过两个；中断后用 SendMessage 让原 agent
  从 worktree 的半成品续跑（改动不会丢）；快完成的先恢复，大任务后恢复。
- **防睡眠进程可能被终止** — 后台的 `caffeinate -ims` 以退出码 144 结束过一次；看到它的 task-notification
  立即重挂，并用 `pmset -g assertions` 确认断言生效。

- **给无 Claude Code 的机器打包**：
  - setup 脚本要把目标机器上**所有**运行时依赖装齐，包括本机从基础环境继承、所以 requirements 里没写的那些（例如 torchvision、accelerate）；
  - prefetch 要覆盖测试会读的全部小文件（含 `*.md`）；
  - 启动脚本显式设 `OMP_NUM_THREADS`；
  - 权重按清单核对哈希；
  - 环境改动之后，要求重跑一遍全量测试。

  做法：先在一台干净的 venv 里按包的说明从头跑一遍，再上传。

## 数据获取（共享机、外部源）
- **先探体积再下载；zip 用 Range 抽取 central directory 定点取文件**，省 99% 流量。
- **公共 Drive 配额按文件计、随请求大小退化** — 探针要探真正的大文件并用 ≥256 KiB 请求；
  用户"复制到自己云端硬盘"得到的新文件配额独立，服务器可直拉，零用户带宽。
- **派生 cache 验证通过后再删原始数据**，校验和留档；删除前从张量独立复算，不采信构建日志。
- **HF hub 1.x 的缓存 blob 是全局共享的**：大文件在 `hub/blobs/` 下，`models--X/` 里只有符号链接。只删
  `models--X` 腾不出空间，还会留下孤儿 blob。删模型用 `scan_cache_dir(dir).delete_revisions(sha).execute()`，
  先 dry-run 看预计释放量。
- **两阶段监管**：窗口内正常轮询，到限后降频探针而非全停——配额可能任何时刻恢复。
- **无人值守脚本先用 stub 隔离验证控制流**（过期+关 / 过期+恢复 / 未过期三种场景）。
