# 开发 CC

你在开发机上，收到的 `[DEV-TASK NNNN]` 是管理员写的任务书（全文也在 `prompts/dev/NNNN-*.md`）。

- **只做任务书里的事**。任务之外你觉得"顺手该做"的，写进完成总结里建议给管理员，不要直接做。
  规格通常禁止造通用框架——每小时花在扩展性上都是从实验偷走的。
- 动手前读规格文件的硬约束小节与 `DECISIONS.md`，它们是规格的唯一来源；任务书引用的
  D 编号先读一遍。
- **不 commit、不 push。** 工作区与管理员共享，git 由管理员统一管理，每个 commit 对应一次审查。
- 约定（网格、索引、命名映射、预处理参数）**只在一处定义、其余 import**；两处各写一份的约定
  迟早分叉。已有常量就引用，不要重述数字；配置注释里的数字要有测试钉住。
- 发现任务书自相矛盾、或任务书的某句话在数值上不成立（如"与 X 完全对齐"其实差 100 倍）：
  不要静默改设计，**在实现里加测试防止过度主张溜回去，然后上报待裁**。
- 跑通任务书里的验收命令再收工；在合成数据上做端到端彩排（真实数据路径的形状与真实
  运行路径一致），不只跑单测。
- **开发机上不可能产生差异的属性（device、dtype、内存布局、对象同一性），测试等于没写** ——
  `assert x.device == "cpu"` 在 CPU 机上删掉被测代码照样绿。这类属性要两条腿：
  ① 代码里的**入口断言**（进算子之前比较，抛自有异常并报出两个值，任何机器都会触发）；
  ② 算力机上的**一次运行期审计**（hook 挂满子模块，首个不符即停并报模块名）。
  开发机端用 `meta` 设备做可观测代理：模块搬到 meta、输入留 cpu，纯 Python 的断言照样触发。
  测试 fixture 不要把同一个对象同时塞给两处（真路径上它们是两个实例）。
- 完成总结固定结构：改了哪些文件、每个做什么、验收结果（含测试数）、**逐条偏离待裁定**、
  遗留/建议。最后一句："已完成，请交给管理员检查"。
